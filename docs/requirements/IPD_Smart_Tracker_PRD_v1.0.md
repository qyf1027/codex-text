# IPD Smart Tracker — 产品开发需求文档（PRD）

> 文档版本：V1.0 · 2026-10-23  
> 交付类型：可用于产品开发、编码实现与验收的 Markdown 需求基线  
> 产品定位：本地优先、单人使用的多项目 IPD 进度跟踪与智能排期应用  
> 需求状态：**本轮功能范围收敛**；本文标注为“实现约定”的细节属于为消除歧义而作的开发默认，不等于用户额外提出的新功能。  
> 优先级解释：P0＝V1 必须实现；P1＝V1 应实现但可在功能闭环后完善；Out＝本版明确不做。

## 0. 开发人员先读：要交付什么

开发一款**真正能够运行、持久保存数据、支持多项目关联和可解释智能排期**的个人 IPD Smart Tracker，而不是只完成页面原型。应用必须能够由用户创建多个项目及任务、维护阶段 GA、定义阶段性成果及跨项目依赖，基于周一至周五工作日计算日期与风险，计算与采纳智能排期建议，记录真实执行，管理少量关键受限资源，备份/恢复 JSON；发生排期不可能或依赖失效时如实给出预警与条件性补救建议。AI（Gemini）仅是可选建议入口，不能决定性影响计算正确性。

**现有输入与工程约束**：用户此前指定以 `ipd-smart-tracker.zip` 为功能/视觉基准，技术栈 React + TypeScript + Vite，应用位于独立的 `/workspace/ipd-smart-tracker` 目录，不将 `codex-text` Skill 仓库混入。开发时如实际收到 ZIP，应先核查并保留可用代码与界面风格；如未收到 ZIP，**不得假称已检查或复用**，按本文实现可用版本并记录基准缺失。允许在现有工程基础上补充必要库，但不得把本地优先的核心排程交给不可用的外部服务。

**交付判定**：功能在刷新浏览器后仍可使用；数据可导出并在新环境导入恢复；任务/成果/资源跨项目变化可触发一致的重算；智能建议与真实记录不混淆；典型和边界验收案例通过；项目可构建、可运行，并有明确使用与测试说明。

### 0.1 决策优先级与冲突处理

1. 本文“已确认业务规则”优先于旧设计截图中的相冲突规则；未被更新的旧要求保留。
2. **计划、建议、采纳、实际、风险历史互不覆盖**。用户实际行为可以偏离计划，但系统必须标出偏离及其风险。
3. 排程算法只能操作可调整的未来安排，不能自动修改已发生事实、已交付成果及用户已采纳计划。
4. 时间、工期、资源占用和依赖关系计算应是**可确定、可重复、可解释**的本地算法；AI 不得代替它。
5. 对尚未讨论的边界情况采取最小可行实现，并在文档/界面中明确限制，不为填满功能而发明新的审批系统。

## 1. 产品背景、目标、边界

### 1.1 使用对象与典型场景

主要用户为一位同时跟进多款硬件产品（如吹风机、扩香仪、雪茄柜）的 IPD 产品经理。用户可能同时管理设计、打样、测试、认证、包材、量产准备等跨部门任务，需要随时知道：哪个成果尚未交付、哪些任务被阻塞、是否影响某个 GA、是否有赶工空间、多个项目是否争抢同一受限资源，以及原始风险与实际进度分别是什么。

这不是多人在线 OA、审批或完整 ERP/MES；“任务负责人”只是记录信息，不代表该负责人负责全部实际执行时间。

### 1.2 业务目标（P0）

- 对多个项目的任务、成果节点、阶段和 GA 形成统一且可追踪的数据结构。
- 在存在多重前置成果、阶段性交付、成果失效、跨项目依赖的条件下给出一致的依赖判断。
- 按工作日计算**标准预测**、**智能优化建议**、**已采纳执行计划**和**实际进度**，并持续保留最初风险。
- 识别 GA 延期、硬截止不可达、依赖未满足就提前开工、失效成果、关键资源冲突等问题。
- 对资源冲突及 GA 风险生成**可计算的候选方案**，由用户确认后再采纳；不可行时不伪造成功排期。
- 本地持久化、导出、导入和完整备份；没有 AI Key、没有网络时仍可管理项目和排期。

### 1.3 非目标（Out）

多人协作、云账号与多端实时同步、审批流、供应商实时反馈集成、自动抓取外部测试资源报价、完整工时核算、小时级设备排班、国家法定节假日自动更新、自动生成项目所需文档、让 AI 直接修改正式排期、自动承诺 GA、对所有补救措施进行全组合最优搜索。营销、市场预测及技术认证不是排期数据的事实来源。

### 1.4 V1 范围划分

| 级别 | 能力 |
|---|---|
| P0 | 本地多项目工作区、阶段/任务/GA、成果节点、依赖图、工作日排程、智能建议及采纳、实际记录、风险历史、关键资源冲突、JSON 备份/导入、异常校验 |
| P1 | 更方便的可视化差异比较、历史版本回看、批量操作、Gemini 建议体验、跨项目风险总览优化 |
| Out | 全量资源容量优化、AI 自动执行、云同步、多人权限、实时外部数据、自动穷举所有补救组合 |

## 2. 核心术语与数据语义

**工作区 Workspace**：本地数据容器，包含多个项目、全局资源及跨项目引用。一个工作区中各对象 ID 全局稳定，不能用名称作关联。

**项目 Project**：完整的产品开发对象，有项目名称、起始日期、项目优先级、阶段、任务及 GA。

**阶段 Stage**：IPD 流程中便于组织的任务集合；应支持按既有项目基准配置阶段名称/顺序，不硬编码为不可编辑的标准流程。

**GA/Gate**：项目阶段/上市等关键目标节点，包含目标日期和“普通目标/硬截止”类型。目标日期与实际达到日期分别记录；不能仅因预计日期到达而自动判定通过。其完成判据由显式关联的任务/必需成果确定；未配置完成判据时，必须由用户手动确认实际达到。

**任务 Task**：管理工作的基本单位；包含标准工期、最短工期、计划与实际状态，允许 0～N 个成果节点。

**成果节点 Deliverable**：任务在过程中或结束时交付的可检查成果，不是独立计数的任务。成果可以为“必需成果”或“普通成果”，并可作为任何项目后续任务/成果的前置条件。

**依赖 Dependency**：以成果是否有效交付为主要条件的链接。普通任务可通过“任务完成”这一虚拟完成信号被依赖；无须强制每个任务手工创建成果节点。

**关键资源 Resource**：用户显式登记的、在指定日期区间不可被两个任务同时独占的受限设备/人员等。普通负责人字段不自动形成独占资源。

**标准预测 Baseline/Normal Forecast**：在不使用额外赶工假设的条件下，按照标准工期与当前客观信息计算的日期。需区分冻结的原始基准快照和随实际进度更新的标准预测。

**智能建议 Proposed Schedule**：算法提出的未来排程/压缩/错峰方案，未被确认时不等于执行计划。

**已采纳计划 Accepted Plan**：用户确认采用的未来执行安排，可用于跨项目排程参考，但不是实际完成，更不是外部机构履约承诺。

**实际 Actual**：用户输入且已真实发生的开始、交付、完成日期；排程引擎不得改写。

**风险 Risk**：包括仍活跃、已有缓解措施和已解除的事件记录。风险解除也不删除原事件及其首次出现时的事实。

## 3. 工作区与项目管理（P0）

### 3.1 工作区

- 首次打开应用，创建一个默认本地工作区；提供“新建项目、切换项目、项目概览、工作区备份/恢复”。
- 可以在同一浏览器本地保存多个项目，跨项目依赖能访问所有存在于工作区的成果。
- 当前查看一个项目时，界面仍能看到其直接跨项目依赖和相关风险；提供切换到源项目的入口。
- 删除项目属于高风险操作：先显示被其他项目引用的任务/成果数量；要求明确确认；不得静默删除下游引用。删除后下游引用保留为“依赖缺失”的可修复占位，并产生预警。建议优先提供“归档项目”而非删除；归档不影响依赖解析。
- 所有编辑在本地自动保存；刷新后保留工作区、已采纳计划、实际与风险历史。

### 3.2 项目基础字段

| 字段 | 要求 |
|---|---|
| `id` | 不变的 UUID，工作区内唯一 |
| `name` | 必填，可更名，改名不影响关联 |
| `startDate` | ISO `YYYY-MM-DD`，工作日基准起点 |
| `priority` | 高 / 中 / 低；仅辅助比较，不能突破硬约束 |
| `description` | 选填 |
| `status` | 进行中 / 已归档（不自动删除） |
| `stages` / `gates` | 有序阶段及 GA 节点 |
| `createdAt` / `updatedAt` | 审计时间戳 |

### 3.3 阶段与 GA

- 阶段可更名、排序、添加；各任务指定所属阶段。
- 一个阶段可配置 GA 卡片；GA 明确 `targetDate`、`deadlineType=soft|hard`、`actualAchievedDate?`、关联完成判据。
- GA 的当前预计完成日期从**明确关联的关键任务/必需成果**推算（多个取最大预计完成时间），或在未配置判据时提示“缺少自动预测依据”，绝不能用未说明的任意任务推算。
- 目标日期、当前预测日期、已采纳预计日期与实际达到日期不能混淆。
- 更改 GA 类型/目标日期需要记录变更；原目标与原始风险仍可回看。

## 4. 任务管理（P0）

### 4.1 任务字段

| 字段 | 规则 |
|---|---|
| `id`, `projectId`, `stageId` | UUID 及归属；ID 不因编辑/排序改变 |
| `title`, `description`, `ownerNote` | 名称必填，其余选填；负责人只是说明，不参与默认资源冲突计算 |
| `standardDurationDays` | 正整数，工作日；默认 1 |
| `minimumDurationDays` | 正整数，且 `1 <= minimum <= standard` |
| `status` | 未开始 / 进行中 / 已完成 / 已取消；阻塞/风险属于派生标识 |
| `actualStartDate`, `actualFinishDate` | 可人工录入/纠错；系统不自行填写 |
| `remainingWorkdays` | 进行中任务可选填的预计剩余工作日数；用于预测，不代表实际记录 |
| `manualDelayWorkdays` | 未完成任务选填的额外延期工作日数；影响标准预计，不改变原始基准 |
| `notes` | 支持备注，包括延期原因 |
| `deliverableIds`, `dependencies`, `resourceBookings` | 关联信息 |

**日期校验**：日期用本地日历日期而非 UTC 午夜时间戳存储；开始不晚于完成。实际可发生在非工作日，应如实允许记录并给出非工作日提示，不因排程规则禁止现实。编辑已经发生的日期须保留修改历史。

**完成操作**：仅在所有必需成果的当前有效版本已交付，且所有未交付普通成果已被处理后，允许用户确认任务完成并填写实际完成日期。若无必需成果，可以直接人工确认完成。系统不得因为已满足成果条件就自动填实际完成日期。

**剩余工期与延期输入的优先关系（实现约定）**：未开始任务以标准工期 + 用户显式的额外延期计算标准预计；进行中任务如果填了 `remainingWorkdays`，使用真实进度日加预计剩余时间推算，**不重复叠加原先同一原因的延期数**；若未填剩余工期，按工期和实际开始日计算并显示为粗略估计。已完成任务以真实完成日为准，不再套用预计工期。

### 4.2 普通成果的任务完成前处理

任务准备结束时如仍有普通成果未交付，系统必须弹出处理选择：

1. **取消成果**：说明不再需要交付，保留原因与历史；若存在下游引用，先提示影响并生成“前置成果取消”的待处理依赖风险，不释放依赖。
2. **转移成果**：转给工作区内另一任务继续交付；保留成果原 ID、原始来源及依赖引用；检查转移造成的跨任务/跨项目环路，更新预测。
3. **暂不结束**：任务保持原状态，不强制取消成果。

取消和转移都不能把成果自动视为“已交付”；必需成果的取消必须先明确修改验收条件并留下审计记录，不能在完成对话框中静默跳过。

## 5. 成果节点模型（P0）

### 5.1 成果字段与状态

| 字段 | 含义与校验 |
|---|---|
| `id`, `taskId`, `name` | ID 稳定，成果属于一项任务；可跨项目被引用 |
| `kind` | `required`（必需）或 `ordinary`（普通） |
| `standardOffsetDays` | 正整数：所属任务开始后第 N 个工作日的标准交付点（包含开始日） |
| `earliestOffsetDays` | 可空；填入时满足 `1 <= earliest <= standard`，作为压缩下限 |
| `actualDeliveredDate` | 成果实际交付日期，须用户确认；不自动推定 |
| `status` | 未交付 / 有效已交付 / 已失效 / 已取消 |
| `version` / `versionHistory` | 可追溯的交付版本与变更记录 |
| `invalidatedAt`, `invalidationReason` | 被主动标记失效时填写 |
| `predecessorOutcomeIds` | 可选：成果级前置依赖；包含同一任务或跨任务/项目成果 |

**核心规则**：同一个任务下的成果**默认独立**，不能假设 A1 必然早于 A2。成果各自有标准交付偏移及可选压缩下限，仅通过显式依赖形成先后关系；不能将任务硬拆成连续阶段按比例压缩。

### 5.2 成果日期计算

- 若任务预计开始日为 D，成果标准第 N 个工作日交付，则日期为 `addWorkdaysInclusive(D, N)`；N=1 对应 D 当日。
- 当所属任务预计开始日移动，尚未交付成果的标准/智能预计随之移动；已经实际交付成果使用真实日期且不移动。
- A1 单独延期，不自动推迟 A2；只有明确设置了 `A1 -> A2` 依赖时才传播。
- 压缩时只能把**未实际交付、允许压缩**的成果在其标准交付点与最早交付点之间调整；空最早日期表示不可自动提前。
- 任务预计完成日期不得早于其所有**必需成果**的预计交付日期；若计算出的最短任务工期无法容纳必需成果下限，应调整候选完成日期或标记当前约束不一致，绝不能静默违反约束。
- 普通成果即使不作为所属任务的完成判据，仍可独立影响下游排程。取消/转移处理必须避免“完成任务后遗失依赖”。

### 5.3 变更、版本与失效

用户修改成果时有两类明确操作：

- **普通版本更新**：记录新版本/说明，既有交付继续有效，不自动触发下游风险。
- **标记原交付失效**：用户确认变更会影响原成果，记录失效时间/原因，系统识别直接及间接依赖的任务与成果，发出潜在影响预警。

影响传播不是自动认定所有下游工作已失效。用户逐个处理受影响项目/任务：`不受影响` / `接受风险继续` / `需要返工` / `暂待确认`。未处理项保持风险状态；已经开始/已经完成的实际记录不能被撤回或自动删除。

成果重新交付 V2 后，依赖 V1 的下游工作**不自动接受** V2。系统提示相关使用方确认是否接纳新版本；确认后依赖引用更新版本或标记“接受当前有效版本”，并保留其原先使用的版本记录。不能因新版本上传而静默消除下游返工风险。

## 6. 任务与成果依赖（P0）

### 6.1 依赖定义

- 依赖从“任务全局串行/并行属性”升级为**一条链接一个条件**。
- 主要依赖类型：`某成果的有效交付 -> 某任务可开始`；`某成果有效交付 -> 另一成果可交付/进入后续步骤`。
- 为避免强迫所有任务设置成果节点，支持 `某前置任务实际完成 -> 后续任务可开始` 的兼容依赖（视为虚拟完成成果）。
- 一个任务/成果允许依赖多个上游条件，默认必须**全部满足（AND）**；V1 不要求任意 OR 逻辑。
- 依赖允许跨项目，引用采用 UUID，不用项目名/成果名称关联；必须校验目标存在与状态有效。
- 无前置条件的任务可以从项目起始工作日开始，或在用户明确设定的开始约束后开始。非工作日项目起始日期先顺延到下一个工作日参与计划计算。
- 新建依赖时检查**整个工作区**的依赖图，禁止循环依赖，包括跨项目环路。任务内成果独立，不应因共享父任务而被错误判定循环。

### 6.2 计划与实际的不同规则

- **计划/智能建议**：必须满足有效的前置成果条件。未交付时可以使用上游**预计交付日**安排未来任务，但须标记“预计依赖，尚未真实满足”；默认最早从交付后**下一个工作日**开始。
- **实际记录**：即使依赖尚未满足，用户仍可以登记任务已开始的真实日期；系统触发“提前启动，依赖未满足”风险并保持记录。
- **进行中提前启动的任务**：智能排期承认其已开始，不把任务重新排到未来的“未开始”状态；使用预计剩余工作日计算完成时间，同时保留依赖异常风险。
- **成果失效/取消/缺失**：未开始的下游计划不能把旧成果当成有效条件；显示阻塞或“待确认”状态。已开始任务继续显示真实进度和潜在返工风险，不被自动暂停。
- **已经接受风险 ≠ 依赖已满足 ≠ 风险已解除**：三者应在数据和 UI 中独立表示。

### 6.3 依赖缺失的容错

导入单项目、删除源项目、错误引用等导致上游对象不存在时：

1. 保留原引用 ID 与可显示的原名称快照；显示“依赖来源缺失”。
2. 阻止将该缺失依赖当成已满足；对应候选排期标注数据不完整。
3. 允许用户重新绑定到工作区已有成果，或明确删除依赖并记录理由；不能暗中删除边。

## 7. 工作日历与计算基准（P0）

### 7.1 日期规则

- V1 固定**周一至周五为工作日**，周六和周日不安排新的计划工作日；**不要求法定节假日库**、不输入法定节假日。
- `YYYY-MM-DD` 作为纯日历日期进行运算，避免浏览器本地/UTC 转换造成前后一天误差；显示随用户当地日期格式，但数据格式不变。
- 开始日占第一个工作日：起始 10 月 26 日（周一），耗时 1 工作日的任务标准完成日就是 10 月 26 日；耗时 3 日则为 10 月 28 日。
- 若前置成果 10 月 28 日交付，默认后续任务最早 10 月 29 日启动；若次日为周末，则到下一个周一。手动提前实际启动仍可登记并触发依赖风险。
- 所有延误、工期压缩、缓冲余量采用**工作日**口径并在 UI 标注；历史事件记录精确时间戳用于审计，但排期日期使用纯日历日期。

### 7.2 三种日期来源与原始基准

| 视角 | 使用数据 | 是否允许算法改写 |
|---|---|---|
| 原始基准 | 初次确认的任务/成果/GA 日期和标准工期快照 | 否，改计划只生成后续版本 |
| 当前标准预测 | 当前真实进度、已确认输入、标准工期、成果与资源约束 | 可重算，不覆盖原基准 |
| 智能候选排期 | 当前状态 + 允许的压缩/错峰措施及约束 | 可重算，用户未采纳前只是建议 |
| 已采纳执行计划 | 用户确认的一版完整候选安排 | 不自动改写；用户重新采纳才产生新版本 |
| 实际 | 用户确认的实际开始、交付、结束、GA 到达日期 | **绝不**由算法改写 |

UI 可以保留原有“警告/智能排期/实际”主要栏目，不要求将上述视角全部展开为永久大宽表。原始基准与计划版本可在详情、对比和历史中查看。

## 8. 智能排期与压缩算法（P0）

### 8.1 输入与输出

**输入**：项目/任务/成果/GA、当前日期、原始基准、已采纳计划、实际日期、任务标准与最短工期、成果标准和最早交付偏移、依赖关系、用户填写的剩余工期/延期、关键资源占用及当前不可移动约束。

**输出**：当前标准预测；活跃风险和历史风险；一个或少量有解释的候选调整方案；每项方案对任务、成果、资源、项目 GA 的变更及原因；可行性/前提假设；采纳后生成的执行计划版本。

### 8.2 基础排程流程

1. 校验字段与引用完整性；跨工作区构造有向依赖图，检测循环。
2. 按拓扑顺序推算任务最早预计开始日、成果预计交付日、任务预计完成日。上游多个依赖取全部满足后的最晚允许启动日。
3. 融合实际情况：已完成的真实日期固定；进行中以实际开始及剩余工期估计；未开始使用标准/当前约束。已交付成果实际日期固定。
4. 对拥有独占资源的任务计算未来资源占用区间；检查重叠并登记冲突。纯时间重叠的普通任务不构成资源冲突。
5. 自下而上计算各 GA 的预计日期，对比普通目标/硬截止；保留初次发现的风险与当前风险，生成风险来源链。
6. 当前标准排程完成后才尝试优化，不能先压缩再把“赶工方案”当成正常预测。

**最早开始与完成的基本口径**（不考虑已实际提前开始这一特殊情况）：

```text
ES(task) = max(projectStart, nextWorkday(each predecessor effective/estimated date),
               any explicit future start constraint)
EF_standard(task) = inclusiveWorkdayEnd(ES, standardDuration + eligible extra delay)
EF(task) >= max(estimated date of all required deliverables)
```

成果交付日期亦须满足它自己的上游成果依赖；有资源独占预约时再应用资源可行性检验。若存在未满足且没有可信预计日期的前置条件，输出“预计无法确定”而不是凭空给一个日期。

### 8.3 压缩策略

- 先找出会影响目标 GA 的依赖链/紧约束任务，再考虑压缩；避免为所有任务平均减少工期。
- 仅尚未完成的剩余工作可压缩；已完成部分、已交付成果、已实际占用资源不参与追溯压缩。
- 任务工期不得小于最短工期；成果不得早于设置的最早可交付日。成果未设置最早时间则不自动提前。
- 压缩某任务时，独立成果不被按比例同步压缩；只有约束要求且成果可压缩时，才调整该成果。
- 每次候选调整后重新计算完整受影响依赖链和 GA；无法消除硬截止冲突时明确显示仍不可达，不伪造可行性。
- 没有严格证明全局最优所需条件时，只应写“找到符合约束的候选方案/启发式建议”，不能保证数学意义的最优解。

### 8.4 已采纳方案与重算

- 用户确认采纳前，展示变更列表（项目、任务/成果、日期前后、资源冲突变化、各 GA 影响、不可行/未验证条件）。
- 涉及多个项目的方案**一次性整体采纳或整体取消**；禁止只更新其中一部分造成新冲突。
- 采纳生成 `planRevision`，记录旧版、变更、时间与备注；**不覆盖**原始基准、此前采纳版本、真实记录和风险历史。
- 上游已采纳计划改变时，下游标准预测/候选建议可以重算，但其他项目已采纳计划仍保持原值；若变得不可执行则显示“已采纳计划冲突”风险，并建议重新采纳。
- 用户确认采纳不代表外部供应商承诺，更不代表实际已交付。

### 8.5 跨项目传播

- 任意项目的成果预计/实际日期变化、成果失效、资源预约变更会触发依赖项目的定向重算；必要时重算整个受影响子图，不能只更新直接邻居。
- 下游项目不能因自身 GA 紧张就擅自修改上游项目的已采纳计划；如确有必要，将上游变更列入**跨项目联合候选方案**，等待整体采纳。
- 计算结果可追溯：界面应能说明“为什么此任务变成该日期”，至少列出限制它的最晚前置成果、剩余工期、必要资源或硬截止冲突。

## 9. 关键资源与跨项目错峰（P0）

### 9.1 数据规则

- 全工作区统一资源库：`resourceId`、名称、备注、`exclusive=true`。V1 只处理用户显式标记的**独占**资源；非独占/普通负责人只展示信息、不强制排程。
- 一个任务可以关联 0～N 个资源占用区间。每条记录包含资源 ID、任务 ID、相对任务工作日起点的占用开始偏移与持续工作日数，或用户锁定的绝对预约日期；只在工作日粒度安排。
- 资源占用应表示真正独占的时间段，而非默认占满整个任务工期。
- 只有同一资源的**未来/未完成独占占用区间重叠**才构成可排程冲突；已经发生的真实占用属于不可回改历史。
- 固定预约与由任务时间推导的预约要区分；不能因为移动任务就擅自移动用户锁定的预约。

### 9.2 错峰建议

- 发现资源冲突时，系统提供可行的提前、推迟、适当压缩或调换顺序候选；必须同时满足成果依赖、任务/成果最短时间、实际固定记录和硬截止。
- **已采纳计划可以参与建议比较，但不能自动被修改**；改变已采纳计划需用户确认形成新版。
- 多项目联合候选展示每个项目预计 GA 是否延期、硬截止是否满足、影响的任务、改变的资源日期与风险变化。
- 选择方案的顺序：先排除违反硬约束的方案；优先寻找所有项目 GA 均按期的方案；无法兼顾时结合项目优先级、GA 影响及已采纳计划改动范围展示取舍。
- 高优先级不等于无条件先用资源；普通目标可以偏移，硬截止不能被算法当作可随意突破的目标。
- 无合规方案时提示“当前约束下没有可行错峰方案”，并保留原因、最早可能完成日期（能计算时）及条件性补救入口。

### 9.3 资源预约的实现约定

V1 以**连续工作日独占区间**为单位进行移动和比较，不做同一天内按小时切分、多人百分比容量或中途拆分测试过程。若一个测试需要多段占用，由用户建立多条占用记录；同日碰撞被视为冲突，即使实际可能错峰半天。界面应明示这是工作日粒度的保守判断。

## 10. GA 风险与硬截止（P0）

### 10.1 GA 类型

| 类型 | 调度语义 | 不满足时处理 |
|---|---|---|
| 普通目标 `soft` | 尽量满足；允许延期候选 | 显示预计延误、原因和建议，可由用户采纳延期计划 |
| 硬截止 `hard` | 算法推荐的“约束内可行”方案不得突破 | 显示“当前约束下不可达”，不可将违规方案标成已满足 |

用户可编辑硬截止目标，但任何修改必须进入历史；对于外部真实不能更改的期限，系统应推荐变更执行条件而非默默延后截止。

### 10.2 风险类别

| 编码 | 触发条件 | 处理原则 |
|---|---|---|
| `GA_DELAY` | 标准预测超过 GA 目标 | 保留基准下延期风险，即使智能建议能追回也不能抹去 |
| `HARD_DEADLINE` | 所有现有约束下硬截止不可达 | 标记不可行，触发条件性补救建议 |
| `DEPENDENCY_UNMET` | 实际提前启动或计划依赖尚未满足 | 保留真实记录，提示依赖风险 |
| `DELIVERABLE_INVALID` | 上游交付用户标记失效 | 标记潜在受影响链，由用户决定是否返工 |
| `DEPENDENCY_MISSING` | 导入/删除后引用对象缺失 | 不视为满足，允许重新绑定 |
| `RESOURCE_CONFLICT` | 同一独占资源的占用重叠 | 产生错峰建议，不自动修改已采纳计划 |
| `ACCEPTED_PLAN_CONFLICT` | 上游变化导致已采纳计划不满足现有约束 | 保留已采纳版本，提示重新评估 |
| `INCOMPLETE_INPUT` | 缺少排程必须的日期/引用或工期不合法 | 不输出假精确预测；提示修复位置 |

### 10.3 风险生命周期

- 风险事件首次触发时写入历史，后续重算更新该事件的当前影响；重复计算不无限生成重复事件。
- 处理状态至少分为：待处理、已有缓解方案、已解除；另保留“用户接受风险”的处理意见，不应把它映射成已解除。
- 风险已解除仍可在历史中查到**首次发现日期、当时延期多少工作日、原因、采纳了哪些措施、解除时间**。
- 预警不要用相同的强烈视觉样式永久突出所有历史事件；当前警告和历史风险分开展示。

## 11. 条件性补救建议（P0 最小闭环，AI 增强 P1）

当硬截止无法满足，或资源冲突缺少约束内可行解时，系统应给出：

1. 当前无法达成的目标、预计差距、最主要阻碍因素。
2. **条件性**改进方向，例如增加外部测试资源、调整其他项目的资源预约、重新确认某项最短工期、拆分独占占用等。建议须明确“待验证条件”。
3. 对条件尚未确认的方案，不能显示为“已解决”，不能直接写入已采纳计划。
4. 用户输入已确认的新资源可用日期/任务工期/约束后，按相同确定性算法**重新模拟**；若可行再按第 8.4 节流程整体采纳。

**V1 边界**：只需支持单项或用户手动组合少量改动后重新计算；无需 AI 自动枚举全部组合，也无需给补救方案凭空估算节省天数。离线时至少有基于风险类型的规则提示与人工调整入口。需要更改外部真实约束时必须让用户明确录入，而不是让系统默认“第三方一定可以做”。

## 12. 页面、信息层级与交互（P0）

### 12.1 页面/区域

| 页面 | 必要信息与操作 |
|---|---|
| 工作区/项目切换 | 新建、切换、归档、导入/导出、工作区项目列表，跨项目风险数量 |
| 项目首页 | 项目名称及目标日期、总体进度、阶段/GA 卡片、当前风险与历史入口、延期/受阻任务、进入任务清单 |
| 任务清单 | 按阶段分组；任务名称、工期、依赖、状态、标准/智能预计、实际日期、延期、备注；支持添加、编辑、排序、删除/取消 |
| 任务详情 | 必需/普通成果、预计与实际交付、版本、前置依赖、受影响下游、资源预约、实际记录与风险处理 |
| 智能排期/方案对比 | 当前标准预测、候选调整、已采纳版、任务/GA 变动摘要、采纳/放弃、约束与假设 |
| 跨项目风险与资源视图 | 冲突源、影响项目、错峰候选、依赖链查看、跳转对应项目 |
| 数据管理/设置 | JSON 导入/导出、备份恢复、版本信息、工作日规则、AI 建议开关与密钥说明 |

### 12.2 首页具体要求

延续原设计中“项目名称/日期—GA 进度—风险与延期提示—按阶段展开任务”的信息架构。优先回答三个问题：目前最需处理的风险是什么、下一个关键 GA 是否能按期、有哪些任务依赖他人的成果。

任务表应允许横向滚动，避免因为字段多而挤压文本；编辑可使用表格单元格或侧边详情，**不得因界面简化遗漏编辑关键字段的入口**。任务多时提供阶段折叠、状态筛选、关键风险筛选。新增任务/成果后不需要刷新页面即可重算。

### 12.3 风险、采纳和实际的交互区分

- 明确区分“建议/未采纳”“已采纳”“实际已发生”；不能只用一个日期单元格同时承载三种含义。
- 实际提前开始某任务：允许保存，紧接着提示依赖未满足，并引导确认风险处理；不能弹窗阻止真实记录。
- 成果失效：先选“普通修改/影响既有交付”，选择后者才发起下游影响追踪。
- 完成任务：必需成果不全则阻止确认完成并列出缺口；普通成果未交付则要求取消、转移或保留任务未完成。
- 采纳智能方案：先展示“变动摘要和跨项目影响”，确认后原子写入新版；失败不得部分提交。
- 自动保存应有已保存/保存失败反馈；删除和高影响变更应有确认或撤销路径。

### 12.4 空状态与异常

没有项目时引导创建或导入；没有任务时可添加；未配置 GA 完成判据时提示“无法自动预测该 GA”；无法连接 AI 时说明核心功能仍可运行；导入无效文件给出明确字段错误；引用缺失显示修复入口而不是崩溃。

## 13. 本地存储、JSON 与迁移（P0）

### 13.1 持久化要求

- 推荐浏览器 **IndexedDB** 作为多项目持久层；现有代码如用 `localStorage`，需要实现兼容迁移，避免升级时清空老项目。具体库可由开发选择。
- 每次有效编辑自动保存；一次多项目采纳使用事务或等效的原子提交方案。
- 工作区级写入失败时提示错误，保留用户可导出的最近有效数据；不得提示“保存成功”却未写入。
- 本地存储不是跨设备同步；用户需自行导出 JSON 在其他设备/浏览器导入。

### 13.2 JSON 格式原则

- 文件顶层必须含 `schemaVersion`、`exportedAt`、`exportType`、ID 和数据实体。
- 支持**完整工作区备份**及**单项目导出**。跨项目依赖随导出携带引用 ID 与可读名称快照；单项目导入若找不到源项目，保留“依赖缺失”状态。
- 导入前校验版本、字段、日期、UUID 唯一性、依赖图循环、工期区间、资源重复引用。错误可定位到项目/任务/字段。
- 对导入策略至少提供“新建导入（避免覆盖）”和“完整工作区恢复（显式确认替换）”。若 ID 冲突，采用可追溯映射重建内部引用或拒绝导入，不得简单随机改任务 ID 而不修复所有边。
- 导出后导入应往返保持同样的任务状态、实际记录、成果版本、依赖、已采纳版本及风险历史；只允许导出时间等元信息改变。
- 不要自动导出或发送用户数据到任何 AI 服务。

### 13.3 参考结构（非唯一序列化格式）

```json
{
  "schemaVersion": "1.0.0",
  "exportType": "workspace",
  "exportedAt": "2026-10-23T00:00:00.000Z",
  "workspace": {
    "id": "ws-uuid",
    "name": "My IPD Workspace",
    "projects": [],
    "resources": [],
    "dependencies": [],
    "riskEvents": [],
    "planRevisions": []
  }
}
```

上例为结构示意，不能将占位 ID 当作生产 UUID。正式 schema 应有清晰的 TypeScript 类型、版本迁移与校验器。

## 14. 推荐领域数据结构与约束（P0）

以下为建议的最小稳定对象结构，允许在代码中拆分文件/字段，但语义不得丢失。

```ts
type UUID = string;
type LocalDate = string; // YYYY-MM-DD; no timezone coercion

type DeadlineType = 'soft' | 'hard';
type TaskStatus = 'not_started' | 'in_progress' | 'done' | 'cancelled';
type DeliverableStatus = 'pending' | 'delivered' | 'invalidated' | 'cancelled';
type DeliverableKind = 'required' | 'ordinary';
type RiskState = 'open' | 'mitigated' | 'resolved';

type Project = {
  id: UUID; name: string; startDate: LocalDate;
  priority: 'high' | 'medium' | 'low'; status: 'active' | 'archived';
  stageIds: UUID[]; taskIds: UUID[]; gateIds: UUID[];
};

type Gate = {
  id: UUID; projectId: UUID; stageId?: UUID;
  name: string; targetDate: LocalDate; deadlineType: DeadlineType;
  requiredTaskIds: UUID[]; requiredDeliverableIds: UUID[];
  actualAchievedDate?: LocalDate;
};

type Task = {
  id: UUID; projectId: UUID; stageId: UUID;
  title: string; standardDurationDays: number; minimumDurationDays: number;
  status: TaskStatus; actualStartDate?: LocalDate; actualFinishDate?: LocalDate;
  remainingWorkdays?: number; manualDelayWorkdays?: number;
  notes?: string; deliverableIds: UUID[];
};

type Deliverable = {
  id: UUID; taskId: UUID; name: string; kind: DeliverableKind;
  standardOffsetDays: number; earliestOffsetDays?: number;
  status: DeliverableStatus; actualDeliveredDate?: LocalDate;
  currentVersionId?: UUID; versionHistory: DeliverableVersion[];
};

type DeliverableVersion = {
  id: UUID; label: string; createdAt: string;
  deliveredAt?: LocalDate; invalidatedAt?: string; changeNote?: string;
};

type Dependency = {
  id: UUID;
  sourceType: 'deliverable' | 'task_completion';
  sourceId: UUID;
  targetType: 'task_start' | 'deliverable';
  targetId: UUID;
  acceptedSourceVersionId?: UUID; // can be updated with explicit user confirmation
};

type Resource = { id: UUID; name: string; exclusive: true; note?: string };
type Booking = {
  id: UUID; resourceId: UUID; taskId: UUID;
  anchor: 'task_relative' | 'fixed_date';
  offsetDays?: number; fixedStartDate?: LocalDate; durationWorkdays: number;
  actualOccupiedDates?: LocalDate[];
};

type PlanRevision = {
  id: UUID; createdAt: string; basedOnRevisionId?: UUID;
  affectedProjectIds: UUID[]; changes: PlanChange[];
  adoptedByUser: true; note?: string;
};

type RiskEvent = {
  id: UUID; type: string; sourceId: UUID;
  firstDetectedAt: string; lastEvaluatedAt: string;
  state: RiskState; initialSnapshot: unknown;
  latestSnapshot: unknown; resolutionNote?: string;
};
```

实现必须补全 `Stage`、`PlanChange`、`Workspace`、任务成果变更历史和资源预约审计等具体类型，并提供运行时校验。以上 `PlanRevision` 与 `RiskEvent` 的内容不得以裸 `unknown` 在业务逻辑中直接使用；示例 `unknown` 代表仍需在代码中定义结构化快照类型。

**关键不变量**：

- ID 全局唯一；关系存在且无有向环；成果仅有一个当前所属任务，但可被任意数量的其他任务/项目依赖。
- `minDuration <= standardDuration`；成果 `earliestOffset <= standardOffset`；实际结束不得早于实际开始。
- 标为已完成任务应有用户确认的实际完成日；算法不能将状态自动改为已完成。
- 关联必需成果未有效交付时，不允许新确认任务完成；成果失效不自动撤销历史完成事实。
- 资源占用不得被采纳方案安排在不可重叠的同一资源时段；当已有两份已采纳计划冲突时保留事实并标记冲突，而非破坏历史。
- 硬截止不可达不得进入 `feasible=true` 的约束内候选方案。
- 所有跨项目变更要么整体成功，要么完全回滚。

## 15. 本地计算模块划分与非功能要求

### 15.1 推荐模块

1. `calendar`：工作日判断、加减工作日、日期差（纯函数）。
2. `validation`：输入合法性、引用完整性、依赖环检测、JSON schema。
3. `dependency-graph`：全工作区任务/成果图、影响范围、拓扑排序。
4. `forecast-engine`：基准预测、实际融合、成果日期传播、GA 计算。
5. `resource-engine`：独占预约冲突检测、错峰候选校验。
6. `optimization-engine`：允许的最短工期/成果提前、硬约束检查、启发式候选。
7. `risk-engine`：预警生命周期、风险来源、历史保留。
8. `storage/import-export`：本地事务、版本迁移、备份恢复。
9. `ui`：项目/任务/成果/风险/智能排期页面；业务计算不可散落在各 React 组件里。
10. `ai-advice`：按需调用 Gemini 的可选、非权威建议层。

### 15.2 技术与质量

- React + TypeScript + Vite；采用严格 TypeScript 设置，关键业务状态避免 `any`。
- 计算逻辑应有纯函数/单元测试，UI 使用统一状态源；重新计算应可重复（同输入同输出）。
- 数据规模目标（开发验收约定）：至少可流畅管理 **10 个项目、每项目 100 项任务、每任务平均 3 个成果**；复杂优化可设置明确候选数量/计算次数上限，禁止浏览器无响应或无限循环。该数量是最低性能测试数据，不是产品硬性容量上限。
- 对错误日期、循环依赖、损坏 JSON、存储失败提供用户可理解提示；正常操作不出现白屏。
- 界面优先可读性与编辑效率，电脑端可用；移动端如未专项设计，至少避免核心数据被完全遮挡，但不要求原生移动 App。
- 无网络、没有 Gemini 密钥时，所有 P0 的确定性计算、保存、恢复和风险识别正常运行。

## 16. Gemini / AI 建议（可选增强，不进入排期内核）

用户主动点击“询问 Gemini”时，可以向其提供**经用户确认发送的必要脱敏摘要**（风险类型、GA 差距、任务依赖与资源约束摘要），请其提出可验证的改善方向、可能遗漏的风险及所需确认的外部条件。

- AI 输出必须标注“建议，未经验证”；不得自己更改任务、成果、资源、GA、已采纳计划或实际数据。
- AI 不直接生成被视为可信的确定性日期；任何用户选定的新条件进入排程后仍由本地引擎重新校验。
- AI 调用失败、超时、未配置密钥时提供明确提示和离线规则建议，不影响核心功能。
- 不得硬编码生产密钥进仓库或导出的 JSON；本地输入密钥时给出安全提示，默认不永久保存；不可在未获用户确认时把整份工作区上传。
- 不要求 AI Studio 历史对话、云端后台或特定用户账号才能让应用运行。

## 17. 验收标准与测试用例（必须可复现）

### 17.1 验收方法

每条用例至少包含输入、操作、期望结果，并能在刷新浏览器/导入导出后再次验证。关键排程测试以**固定日期**执行，而不是依赖执行测试当天的系统时间。项目可以提供种子数据、自动单元测试和 UI 操作检查清单。

### 17.2 核心案例表

| ID | 场景与输入 | 期望行为 |
|---|---|---|
| AT-01 | 2026-10-26（周一）起，任务标准 3 工作日 | 标准预计完成 10-28（周三），不把开始日多算一天 |
| AT-02 | 前置成果周五 10-30 交付 | 依赖任务最早计划周一 11-02 开始 |
| AT-03 | 任务标准 2、最短 3 | 拒绝保存并指出最短不能大于标准 |
| AT-04 | A/B 两项目，B 依赖 A 的成果 | A 的预计交付变动会更新 B 的预测和风险，B 的实际不被覆盖 |
| AT-05 | 任务含互相独立的 A1、A2；A1 延期 | A2 不因同父任务而自动推迟，除非额外设依赖 |
| AT-06 | 一个成果依赖两个不同成果 | 两者都满足后，后续任务才解除真实依赖风险 |
| AT-07 | 形成 A→B→C→A 跨项目环路 | 保存新依赖时拒绝，原有效关系不丢失 |
| AT-08 | 必需成果未交付，用户尝试结束任务 | 显示缺失成果，不确认完成 |
| AT-09 | 普通成果未交付，用户结束任务 | 必须选择取消、转移或暂不结束；取消不释放下游依赖 |
| AT-10 | 任务无必需成果，用户完成 | 可人工确认并记录实际结束日期 |
| AT-11 | 成果交付 V1，随后普通版本修改 | 保留有效交付，不自动产生依赖失效风险 |
| AT-12 | 用户主动标记 V1 失效 | 扫描直接/间接下游并提示潜在影响，实际记录不改 |
| AT-13 | V2 重新交付 | 下游原 V1 引用不能自动全部升级；需要逐项确认 |
| AT-14 | 前置未交付，下游任务实际已开始 | 允许记录真实开始，触发依赖预警，进行中任务不重排为未开始 |
| AT-15 | 任务标准 10、最短 7；成果标准第 8 天、最早第 6 天 | 可提出符合成果限制的压缩；不得简单统一按比例缩短所有成果 |
| AT-16 | 成果未设置最早交付时间 | 不自动提前该成果；可能导致 GA 仍有风险 |
| AT-17 | 标准排期 GA 晚 5 天，优化候选追回 5 天 | 原始延期风险仍可查看，候选不伪装成标准预测 |
| AT-18 | 用户采纳优化方案 | 生成新版本；原基准、风险历史、实际记录全部保留 |
| AT-19 | 上游已采纳计划变化，使下游已采纳计划不可达 | 下游已采纳日期不自动改写，出现“已采纳计划冲突” |
| AT-20 | 两项目未来独占同资源同工作日 | 检出资源冲突并提供可行候选；不把普通负责人同名视为独占冲突 |
| AT-21 | 设备只被任务占用 2 天而任务总工期 8 天 | 检测只依据真实预约 2 天，不把 8 天全部锁住 |
| AT-22 | 已采纳 A/B 联合错峰方案 | 多项目变动原子保存；若提交失败全部回滚 |
| AT-23 | 高优先级 A 尚有 4 天余量，中优先级 B 无余量 | 不无条件先给 A 资源，应展示 B 先执行的可行方案与 GA 影响 |
| AT-24 | 硬截止早于所有约束下最早 GA | 标记“不可达”，不能将违规方案标记为可行 |
| AT-25 | 硬截止不可达，第三方资源尚未确认 | 可展示条件性补救，但不得立即按假设新资源写入正式计划 |
| AT-26 | 用户确认新资源日期后重算 | 本地算法检验完整依赖、资源、GA；结果可行才允许采纳 |
| AT-27 | 单项目导入含对其他项目的引用，但源项目不存在 | 以“依赖缺失”保留引用并提示修复，不把它当作已满足 |
| AT-28 | 完整工作区导出后，在空环境恢复 | 任务、成果版本、依赖、风险历史、计划版本和实际均一致 |
| AT-29 | 用户刷新/关闭再打开浏览器 | 本地数据、当前工作区及已采纳计划仍存在 |
| AT-30 | 没有联网或未配置 Gemini | 所有本地 P0 功能仍可用，AI 入口明确提示但不白屏 |
| AT-31 | 将项目、成果改名 | UUID 关联保持不变，不丢跨项目依赖 |
| AT-32 | 实际某任务周日开始 | 允许如实保存；计划排程仍用工作日规则并给出提示 |
| AT-33 | 反复执行同一风险重算 | 不重复创建大量相同活动风险事件，历史首次触发信息保留 |
| AT-34 | 导入损坏 JSON/不受支持版本 | 拒绝不完整导入，旧数据不被污染，错误提示明确 |
| AT-35 | 任务实际完成后修改其标准工期 | 不重写实际记录；原始基准继续可回溯 |
| AT-36 | 进行中任务填写预计剩余 5 工作日 | 预测使用剩余工期，不重复计算已经消耗的工作日或额外延期 |
| AT-37 | 从别的任务转移成果 | 成果 ID 和下游引用不变，重算预计交付并校验循环依赖 |
| AT-38 | 已完成任务下普通成果被取消且影响其他项目 | 被引用项目出现待处理风险，依赖不会被静默解除 |

### 17.3 特别需要防止的错误

- UI 显示“GA 按期”但计算依赖的关键成果已经失效。
- 压缩结果满足 GA 但违反成果最早交付限制或独占资源约束。
- 修改项目 A 后把 B 的已采纳计划直接覆盖。
- 把用户“接受风险”当成“风险消失”。
- 刷新后丢失成果版本或用户实际输入。
- JSON 单项目导入时静默删除跨项目引用。
- 任务被标记“完成”后未交付普通成果不再有任何下游追踪入口。
- AI 错误建议未经条件验证就变成可执行排期。

## 18. 建议开发顺序与完成定义

> 以下顺序为实现依赖顺序，不额外扩大产品范围。

### M1：基础数据与稳定本地应用

搭建/清理 React + TS + Vite 工程；本地工作区及多项目；阶段/任务/GA CRUD；工作日日期函数；持久化；导出/导入基础 schema。验收：能运行、编辑、刷新不丢，日期计算正确。

### M2：成果与跨项目依赖闭环

成果节点与版本、必需/普通成果、实际交付、取消/转移、依赖图、循环检测、跨项目追踪、失效影响预警。验收：AT-04～14、27、31、37、38 通过。

### M3：可解释的预测、风险与采纳

标准预测、最短工期与成果限制、GA 计算、警告生命周期、智能候选、版本采纳及实际状态独立性。验收：AT-15～19、24、33、35、36 通过。

### M4：受限资源与条件性补救

全局独占资源预约、跨项目冲突、错峰候选、硬截止可行性判断、条件性补救和模拟输入。验收：AT-20～26 通过；无效组合不得被采纳。

### M5：界面打磨、备份与回归

首页风险与 GA 展示、任务清单和详情、方案对比、异常处理、完整备份恢复、弱网/无网检查、可选 AI 建议入口与文档。验收：全量测试通过，界面可正常操作，编译构建无错误。

### 18.1 完成定义（Definition of Done）

只有同时满足以下条件才可宣称 V1 已完成：

- `npm install` 与项目 `README.md` 指定的启动/构建命令能够成功运行。
- 文档所有 P0 核心业务能力有实际可用入口，不是仅有按钮占位、静态数据或模拟结果。
- 日期计算/循环检测/依赖传播/压缩约束/资源冲突/JSON 往返至少有自动化测试，AT-01～38 覆盖成功或有明确测试结果。
- 原始计划、已采纳版本、实际、风险历史独立保存；典型跨项目变更可正确重算。
- 不依赖 Gemini 才能使用；调用外部 AI 之前明确提示数据发送与密钥安全。
- 不做云同步及多人协作，不把本轮之外的扩展功能作为交付前提。
- 提供 `README.md`（安装/运行、工作日口径、数据备份、安全与限制）、类型定义、关键算法说明及至少一份示例项目数据。

## 19. 已确认决策与实现约定清单

### 19.1 已由产品讨论确认的决定

| 议题 | 最终决策 |
|---|---|
| 多成果 | 一个任务可包含多个阶段性成果；默认相互独立 |
| 成果触发依赖 | 采用成果驱动，支持一个下游对象依赖多个成果 |
| 成果类别 | 必需成果与普通成果分开；未交付普通成果需在任务完结前处理 |
| 成果变更 | 用户判断是否影响既有交付；主动标记失效才触发下游预警 |
| 成果失效 | 自动追踪并提示潜在影响，是否返工由用户决定 |
| 未满足依赖提前开工 | 允许登记真实执行，保留依赖风险 |
| 跨项目依赖 | 支持，V1 即有本地多项目工作区 |
| 成果提前 | 可设置最早可交付时间，算法不得超出边界 |
| 智能排期 | 用户确认采纳才成为执行计划；保留基准与实际 |
| 关键资源 | 只管理少量明确标记的受限资源，不做全量工时管理 |
| 资源冲突 | 系统提供错峰建议，用户确认采纳 |
| 优化比较 | 项目优先级与 GA 风险共同考虑，不按优先级机械抢资源 |
| GA 类型 | 普通目标与硬截止两类 |
| 硬截止不可达 | 如实显示不可达，并给出待验证的条件性补救建议 |
| AI | 建议层，不直接改排期/实际；无 AI 依然可用 |
| 风险历史 | 即使建议/采纳缓解了当前风险，仍保留其最初存在的事实 |

### 19.2 为保证可编码而加入的实现约定（非额外功能承诺）

- 日期仅用周一至周五；相对成果第 1 工作日是任务开始日；成果交付后下一工作日才计划启动下游。
- 多个前置成果默认为 AND；不自动提供复杂 OR、小时级排班和成果自动验收。
- 无必需成果的任务可以由用户人工确认完成；GA 未配置自动判据时只能人工确认实际。
- 进行中任务的剩余工期优先于粗略标准工期推算，避免同一延期被重复计入。
- 资源预约可按任务相对日期或锁定日期表示；V1 为工作日独占区间。
- 未验证的补救建议只以假设形式展示，不参与真实可行性判断，直至用户录入明确新条件。
- 推荐使用 IndexedDB；精确 UI 布局与数据实体具体拆分方式允许开发调整，只要不改变这些业务语义。

### 19.3 未经实测的事项

跨项目排程在大量复杂交叉依赖下的性能、最短工期的业务合理性、供应商是否会按提前计划交付、AI 建议的有效性，都需要开发测试或现实验证。本 PRD 定义的是系统**如何记录、计算与提示**，不宣称它能保证某个产品实际如期 GA。
